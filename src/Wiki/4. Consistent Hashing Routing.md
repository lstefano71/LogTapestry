## Introduction
The Consistent Hashing Routing system in LogTapestry is designed to ensure that all events from the same file are processed by the same worker thread, maintaining processing order and preventing race conditions. This document provides a comprehensive analysis of the implementation, configuration, and integration of this routing mechanism within the log ingestion pipeline. The system uses file identifiers and volume serial numbers to deterministically assign files to processors, ensuring consistency across restarts and scaling events.

#### Implementation Details
The ConsistentHashRouter uses a combination of the file ID and volume serial number to create a stable hash value. This approach ensures that even if the application restarts, the same file will be assigned to the same processor, maintaining processing consistency.

```
csharp
public int GetProcessorForFile(ulong fileId, long volumeSerial)
{
    lock (_lock) {
        var key = (fileId, volumeSerial);
        
        if (_fileAssignments.TryGetValue(key, out var processorId)) {
            return processorId;
        }
        
        var hashCode = HashCode.Combine(fileId, volumeSerial);
        var processor = Math.Abs(hashCode) % _processorCount;
        
        _fileAssignments[key] = processor;
        return processor;
    }
}

```

The router maintains an internal dictionary of file-to-processor assignments, which allows for efficient lookups of previously assigned files. The use of a lock ensures thread safety when multiple threads access the assignment dictionary concurrently.

#### Event Routing Logic
The PriorityMonitor implements a priority-based routing system that ensures real-time file system events take precedence over initial scan events. It uses a ConcurrentBag to track files that have already been processed from the fast channel, preventing duplicate processing.


```csharp
private async Task RouteToProcessorAsync(FileEvent fileEvent, CancellationToken token)
{
    var processorId = _hashRouter.GetProcessorForFile(fileEvent.FileId, fileEvent.VolumeSerial);
    
    if (processorId >= 0 && processorId < _processorChannels.Count) {
        var processorChannel = _processorChannels[processorId];
        await processorChannel.WriteAsync(fileEvent, token);
    }
}
```


This implementation ensures that all events for a specific file are routed to the same processor channel, maintaining event order and preventing race conditions during file processing.

#### Channel Management
The ProcessorChannel provides both synchronous and asynchronous methods for writing file events to the channel. The TryWrite method attempts to enqueue an event without blocking, while WriteAsync provides an awaitable operation for guaranteed delivery.

```
csharp
public async ValueTask WriteAsync(FileEvent fileEvent, CancellationToken token = default)
{
    await Writer.WriteAsync(fileEvent, token);
    _logger.LogInformation("Processor {ProcessorId}: Successfully queued {EventType} event for {FilePath}",
        ProcessorId, fileEvent.Type, fileEvent.FilePath);
}

```

Each channel is completed when processing ends, preventing further writes and allowing consumers to detect the end of the event stream.

#### Processing Workflow
The FileEventProcessor implements a continuous loop that reads file events from its channel and processes them sequentially. This ensures that all events for a given file are handled in order by the same processor.


```csharp
public async Task ProcessEventsAsync(ChannelReader<FileEvent> eventReader, CancellationToken token)
{
    await foreach (var fileEvent in eventReader.ReadAllAsync(token)) {
        await ProcessFileEventAsync(fileEvent, token);
    }
}
```


After processing, the resulting DataBlock objects are written to a shared data block channel for batch processing by the sink pipeline.

## Performance Considerations
The consistent hashing routing system is designed with performance and scalability in mind. Several factors contribute to its efficiency:

**Processor Count Configuration**: The number of processors is configured via the FileReaderThreadPoolSize setting in appsettings.json. The default value is set to Environment.ProcessorCount * 2, allowing for optimal utilization of available CPU resources.

**Thread Safety**: The ConsistentHashRouter uses a lock to protect its internal dictionary, ensuring thread-safe access during file assignment. While this creates a potential bottleneck, the operation is typically fast due to the efficiency of dictionary lookups and hash calculations.

**Memory Usage**: The router maintains a dictionary of file assignments, with memory usage proportional to the number of unique files being monitored. For systems with a large number of files, this could become significant.

**Hash Distribution**: The system uses .NET's HashCode.Combine method to create a hash from the file ID and volume serial. This provides good distribution across processors, minimizing the likelihood of uneven load distribution.

**Configuration Example**:
```
json
"Ingester": {
  "FileReaderThreadPoolSize": 8,
  "BatchSize": 50000,
  "PollingIntervalMs": 1000
}
```

The configuration allows tuning of the processor count based on expected workload and available system resources.

## Troubleshooting Guide
When diagnosing issues with the consistent hashing routing system, consider the following common scenarios:

**Uneven Processor Load**: If one processor is consistently busier than others, check the hash distribution. This could indicate that certain files generate significantly more events than others.

**Processor ID Out of Range**: The error "Invalid processor ID {ProcessorId} for file {FilePath}" indicates a mismatch between the hash calculation and the number of available processors. Verify that the processor count configuration matches the number of initialized processor channels.

**Channel Backpressure**: If processor channels are filling up, it may indicate that the processing rate is slower than the event generation rate. Consider increasing the number of processors or optimizing the file processing logic.

**Duplicate Event Processing**: The PriorityMonitor tracks seen events to prevent duplicates from initial scans when real-time events have already been processed. If duplicates occur, verify that file identifiers (file ID and volume serial) are stable across system restarts.

**Configuration Issues**: Ensure that the FileReaderThreadPoolSize setting in appsettings.json is appropriate for your system's capabilities and workload characteristics.
