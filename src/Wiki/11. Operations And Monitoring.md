## Health Checks and System Readiness

The LogTapestry system provides a built-in health check endpoint at `/health` via the **MonitoringService**. This endpoint evaluates two critical system components:

- **Database Health**: Verifies connectivity and responsiveness of the SQLite state database
- **Directory Health**: Confirms the existence of the monitored log directory

The health check returns a JSON response with status and timestamp. A healthy system returns HTTP 200 with:

```json
{
  "status": "Healthy",
  "timestamp": "2025-08-21T10:30:00Z"
}
```


If either component fails, the system returns HTTP 503 (Service Unavailable) with detailed error messages:

```json
{
  "status": "Unhealthy",
  "errors": ["Database check failed."]
}
```


The **SqliteStateProvider.CheckHealth()** method implements database health verification by establishing a new connection and executing a simple `SELECT 1` query. This ensures the database is not only accessible but also responsive to queries.

## Metrics Exposure and Performance Monitoring

The system exposes Prometheus-compatible metrics at the `/metrics` endpoint, providing visibility into ingestion performance and system throughput.

### Exposed Metrics

The following metrics are currently available:

**log_entries_ingested_total**
- **Type**: counter
- **Description**: Total number of log entries successfully ingested
- **Purpose**: Measures ingestion throughput and volume over time

**bytes_processed_total**
- **Type**: counter
- **Description**: Total number of bytes processed from log files
- **Purpose**: Tracks data volume processed and helps estimate storage requirements

**checkpoints_completed_total**
- **Type**: counter
- **Description**: Total number of successful checkpoint operations completed
- **Purpose**: Indicates data consistency and state persistence success rate

### Metrics Implementation

Metrics are implemented as static properties within the **DataSink.Metrics** class:

```csharp
public static class Metrics
{
    public static long LogEntriesIngested = 0;
    public static long BytesProcessed = 0;
}
```


These counters are incremented during the **DataSink.WriteBatchAsync** operation:
- `LogEntriesIngested` is incremented by the batch size after successful writing
- `BytesProcessed` is incremented by the stream length when the stream supports seeking
- `CheckpointsCompleted` is incremented in **CheckpointDataSink.WriteBatchAndCheckpointStateAsync** after successful state updates

The **MonitoringService** formats these metrics in the Prometheus text exposition format, making them compatible with standard monitoring tools like Prometheus and Grafana.

## Logging Practices and Custom Enrichers

The system uses Serilog for structured logging, enhanced with custom enrichers that provide additional context to log events.

### ManagedThreadIdEnricher

This enricher adds the current .NET managed thread ID to each log event, enabling correlation of logs within the same thread context.

```
csharp
public class ManagedThreadIdEnricher : ILogEventEnricher
{
    public void Enrich(LogEvent logEvent, ILogEventPropertyFactory propertyFactory)
    {
        var threadId = Environment.CurrentManagedThreadId;
        logEvent.AddPropertyIfAbsent(propertyFactory.CreateProperty("ManagedThreadId", threadId));
    }
}

```

The enricher adds a property named `ManagedThreadId` with the integer thread identifier, which is invaluable for debugging multi-threaded processing issues and understanding worker thread behavior.

### UtcTimestampEnricher

This enricher adds a formatted UTC timestamp to each log event, ensuring consistent time representation across different time zones.

```
csharp
public class UtcTimestampEnricher : ILogEventEnricher
{
    public void Enrich(LogEvent logEvent, ILogEventPropertyFactory propertyFactory)
    {
        var utcTimestamp = logEvent.Timestamp.UtcDateTime.ToString("yyyy-MM-dd HH:mm:ss.fffZ");
        logEvent.AddPropertyIfAbsent(propertyFactory.CreateProperty("UtcTimestamp", utcTimestamp));
    }
}

```

The enricher adds a property named `UtcTimestamp` with the ISO 8601 formatted UTC time (e.g., "2025-08-21 10:30:00.123Z"), providing a standardized time reference that avoids local time zone ambiguities.

### CSV Parsing Progress Logging

The system has been enhanced with detailed logging for CSV parsing operations, providing visibility into parsing progress and potential issues:

**LogTrace for Parsing Progress**
- Individual log entries are traced with `LogTrace("Parsed log entry from {FilePath}")` in **FileReader.ReadAndCreateDataBlocksAsync**
- No new content is indicated with `LogTrace("No new content for {FilePath}")`
- These traces help verify parsing is progressing and identify files with no new data

**LogWarning for CSV Reading Errors**
- The **CsvLogParser.ParseCsvRecord** method logs warnings for parsing failures with full context:
```
csharp
Logger?.LogWarning(ex, "Failed to parse CSV record: {Line}", line);

```
- Field conversion failures are also logged with warnings:
```
csharp
Logger?.LogWarning(ex, "Failed to convert field value '{Value}' to type '{Type}'", value, type);

```

**LogDebug for Header Processing**
- CSV header processing is logged at Debug level:
```
csharp
Logger?.LogDebug("Processed CSV header with {ColumnCount} columns: {Headers}", 
  _headers.Length, string.Join(", ", _headers));

```
- This provides visibility into column mapping and schema detection

These logging enhancements enable operators to monitor parsing progress, diagnose CSV-specific issues, and verify header processing correctness.

## System Performance Monitoring

Effective monitoring of the LogTapestry system requires attention to several key performance indicators and operational metrics.

### Performance Indicators

**Ingestion Throughput**
- Monitor `log_entries_ingested_total` rate to identify processing bottlenecks
- Sudden drops may indicate parsing issues, file system problems, or resource constraints

**Data Volume Processing**
- Track `bytes_processed_total` to understand data ingestion patterns
- Correlate with ingestion count to identify average log entry size trends

**Checkpoint Success Rate**
- Monitor `checkpoints_completed_total` to ensure data consistency
- Low checkpoint rates may indicate state persistence issues

**Error Rates**
- Monitor log levels for increases in Warning and Error messages
- Pay special attention to file handle exceptions and parsing failures

### Live State Monitoring

The **LiveStateService** maintains an in-memory cache of file positions with SQLite persistence. Key aspects to monitor:

- **Cache Hit Rate**: High cache hit rate indicates efficient position lookups
- **Checkpoint Queue Length**: Monitor the `_checkpointChannel` for backlog, which may indicate database performance issues
- **Batch Persistence**: The service processes checkpoint updates in batches of up to 100, with persistence frequency indicating system load

### Checkpointing Architecture

The system implements a coordinated checkpointing architecture through **CheckpointDataSink** and **StateWriterService**:

- **CheckpointDataSink**: Coordinates data persistence with state updates, ensuring atomic operations
- **StateWriterService**: Monitors checkpoint updates and provides additional logging
- **LiveStateService**: Maintains in-memory state as source of truth, with queued SQLite persistence

## Troubleshooting Common Operational Issues

### Backpressure

**Symptoms**:
- Increasing checkpoint queue length
- High memory usage
- Delayed log processing

**Causes**:
- Database persistence slower than ingestion rate
- Disk I/O bottlenecks
- Insufficient worker threads

**Resolution**:
- Scale database resources or optimize SQLite configuration
- Increase checkpoint batch size in **LiveStateService**
- Monitor and tune the processor channel capacity

### File Handle Leaks

**Symptoms**:
- "Too many open files" errors
- Gradual increase in process file handle count
- System performance degradation over time

**Causes**:
- Improper disposal of **FileReader** instances
- Exceptions preventing proper cleanup in **FileEventProcessor**
- Long-running file monitoring handles

**Resolution**:
- Ensure all **IDisposable** components are properly disposed
- Implement timeout for file operations
- Add file handle monitoring to health checks

### Parsing Bottlenecks

**Symptoms**:
- Low ingestion throughput despite high log volume
- High CPU usage in parsing components
- Accumulation of unprocessed files

**Causes**:
- Complex regex patterns in **RegexLogParser**
- Large multi-line log entries
- Inefficient string operations

**Checkpointing Issues**
- **Failed Checkpoints**: When **CheckpointDataSink.WriteBatchAndCheckpointStateAsync** fails, both data and state updates are rolled back
- **Stale State**: If **LiveStateService** persistence falls behind, restart may process duplicate entries
- **Channel Backlog**: A growing **_checkpointChannel** indicates persistence bottlenecks

**Resolution**:
- Optimize regex patterns for performance
- Adjust buffer sizes in **BaseLogParser**
- Consider parallel processing of independent log files
- For CSV files, ensure proper delimiter and quote character configuration
- Monitor **LogDebug** messages for header processing to verify schema detection
- Ensure adequate resources for **StateWriterService** and **LiveStateService**

## Production Deployment Best Practices

### Resource Allocation

**CPU**: Allocate sufficient cores to handle parsing workload, especially for complex log formats with regex patterns.

**Memory**: Ensure adequate RAM for:
- In-memory file position cache in **LiveStateService**
- Processing buffers in **BaseLogParser**
- Worker thread stacks and local variables

**Disk**: Use fast storage for:
- SQLite database (prefer SSD)
- Temporary processing files
- Final Parquet output files

### Log Rotation and Management

Implement log rotation for the application logs:
- Rotate logs daily or when reaching size thresholds
- Retain logs for at least 30 days for troubleshooting
- Compress archived logs to save space

Configure Serilog to write to both console and file sinks with appropriate rolling policies.

### Backup Strategies

**State Database**: Regularly back up the SQLite database containing:
- Tracked file positions
- Field schema information
- Parquet file inventory

**Configuration Files**: Version control all configuration files, including:
- **appsettings.json**
- Log parser configurations
- Monitoring endpoint settings

**Backup Frequency**: Perform backups at least daily, preferably multiple times per day during peak ingestion periods.

### Monitoring Configuration

Ensure the **appsettings.json** file is properly configured with:
- Correct monitoring URL binding
- Appropriate logging levels for production
- Valid paths for log directories and database files

Example configuration:
```
json
{
  "MonitoringUrl": "http://*:8080",
  "Directory": "/var/log/ingest",
  "DatabasePath": "/data/logtapestry.db",
  "Logging": {
    "LogLevel": {
      "Default": "Information"
    }
  }
}
```
