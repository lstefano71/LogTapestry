## Core Components

The LogTapestry project is a log processing and analytics system designed to efficiently ingest, structure, compact, and query large volumes of log data. It follows a modular, component-based architecture with three primary tools: **Ingester**, **Compactor**, and **Query**. These components work together in a pipeline to transform raw log files into queryable structured data.

The system leverages **Parquet** for efficient columnar storage of structured log data, **SQLite** for tracking ingestion state and metadata, and **DuckDB** for SQL-based querying and compaction operations. The core functionality is abstracted into the **LogTapestry.Core** library, which provides shared data models and interfaces used across all components.

Key architectural patterns include:
- **Component-based design**: Each tool is a separate executable with focused responsibilities
- **Dependency Injection (DI)**: Microsoft.Extensions.DependencyInjection is used for service composition
- **Internal logging**: Serilog provides structured logging with custom enrichers for UTC timestamps and thread IDs
- **CLI parsing**: System.CommandLine is used in the Compactor and Query tools for command-line argument handling
- **Checkpointing**: Atomic data and state persistence ensures consistency between ingested data and tracking state
- **Consistent hashing**: Ensures all events from the same file are processed by the same worker thread
- **Streaming parsing**: New architecture processes log data in chunks via streams rather than loading entire files
- **Worker pool model**: Fixed-size pool of FileReader workers replaces the previous "one-task-per-file" model
- **Priority-based monitoring**: Fast/slow channel architecture prioritizes real-time events over initial scan events
- **Batched state updates**: Position updates are batched and persisted transactionally to reduce SQLite contention

## Priority-Based Monitoring Pipeline

The LogTapestry system has been refactored with a new priority-based monitoring pipeline that fundamentally changes how file system events are processed. The new architecture uses a dual-channel approach with fast and slow channels to ensure real-time events are processed immediately, even during a lengthy initial directory scan.

The new priority-based monitoring architecture provides several key benefits:
- **Low-latency processing**: Real-time file events are processed immediately through the fast channel
- **Startup performance**: Initial directory scan runs in parallel without blocking real-time events
- **Duplicate elimination**: The PriorityMonitor tracks recently processed file IDs to prevent duplicate processing
- **Scalability**: Fixed worker pool model prevents file handle and thread exhaustion with large numbers of files
- **Consistent processing**: All events for a given file are routed to the same processor via consistent hashing

The `DirectoryMonitor` orchestrates three main components:
1. **InitialScanProducer**: Performs a parallelized scan of the log directory, writing `FileEvent` objects to a "slow" channel
2. **WatcherProducer**: Manages the `FileSystemWatcher` and writes real-time file system events to a "fast" channel
3. **PriorityMonitor**: Merges events from both channels, prioritizing the fast channel and eliminating duplicates

The `PriorityMonitor` uses a `ConcurrentBag` to track recently processed file identifiers. When an event arrives from either channel, it checks if the file ID has been recently processed. If so, the event is discarded as a duplicate. This elegantly solves the race condition between the initial scan and real-time watcher.

The state management architecture is built around the `LiveStateService`, which serves as the source of truth for file positions. It maintains an in-memory cache of tracked files and uses a channel-based system to queue position updates for persistent storage.

Key components of the checkpointing architecture:
1. **LiveStateService**: The central state management component that maintains an in-memory cache of file positions
2. **CheckpointChannel**: A bounded channel that queues position updates for batched persistence
3. **Batched Persistence**: Position updates are processed in batches and written to SQLite in a single transaction
4. **StateWriterService**: A monitoring service that processes checkpoint updates for logging and monitoring purposes

The `LiveStateService` implements the checkpointing principle where memory is the source of truth. When a file position is updated:
1. The in-memory cache is updated immediately
2. A checkpoint update is queued to the checkpoint channel
3. A background task processes the channel, batching updates and persisting them to SQLite

This architecture solves the SQLite write contention problem by reducing thousands of individual database transactions to a much smaller number of batched transactions.

The new streaming architecture provides several key benefits:
- **Memory efficiency**: Processes log data in chunks rather than loading entire files into memory
- **Improved performance**: Reduces I/O overhead by processing data as it's read from the stream
- **Better checkpointing**: Enables more granular position tracking for recovery
- **Consistent interface**: All parsers implement the same `ParseNextChunkAsync` method

The `ILogParser` interface defines the core contract:

```csharp
public interface ILogParser : IAsyncDisposable
{
    Task<ParseChunkResult> ParseNextChunkAsync(Stream stream, CancellationToken token);
}
```


Three parser implementations are available:
1. **CsvLogParser**: Implements streaming CSV parsing with internal buffering
2. **RegexLogParser**: Uses regex patterns to identify log entries in a stream
3. **SepCsvLogParser**: High-performance CSV parser using the nietras/Sep library with precise position tracking

The `IPositionAwareLogParser` interface extends `ILogParser` for parsers that maintain their own position tracking:

```csharp
public interface IPositionAwareLogParser : ILogParser
{
    long GetCurrentPosition();
    void UpdateUnderlyingStreamPosition(Stream underlyingStream);
}
```


This is particularly important for the `SepCsvLogParser` which wraps the input stream and needs to track bytes read independently of the underlying stream position.

## Data Flow and Processing Pipeline

The LogTapestry system processes log data through a well-defined pipeline:

1. **Ingestion**: The Ingester monitors configured directories for new or modified log files
2. **Reading**: FileReader opens files temporarily, reads new content since the last checkpoint, and closes them
3. **Parsing**: Log entries are parsed using stream-based parsers that implement the `ILogParser` interface
4. **Structuring**: Parsed entries are grouped into DataBlocks and written to Parquet files with partitioning by date
5. **Checkpointing**: After successful Parquet write, the ingestion position is updated in SQLite
6. **Compaction**: The Compactor identifies partitions older than a threshold and combines small Parquet files into larger ones
7. **Querying**: The Query tool uses DuckDB to execute SQL queries against the structured Parquet data

The system uses consistent hashing to route file events to specific processor channels, ensuring that all events from the same file are processed sequentially by the same worker. This prevents race conditions and allows for natural deduplication of file events.

The new streaming parsing architecture changes how parsing occurs:
- Parsers now process data in chunks via the `ParseNextChunkAsync` method
- The `FileReader` coordinates with parsers to read data incrementally
- Position tracking is handled either by the stream itself or by position-aware parsers
- DataBlocks are created as parsing progresses, enabling more frequent checkpointing
