## Introduction
The Checkpointing Architecture in LogTapestry ensures reliable and consistent state tracking for log processing pipelines. It guarantees that data persistence and state updates occur atomically, preventing data loss or inconsistency during system failures. This architecture combines in-memory state management with durable SQLite storage to provide high performance and reliability. The system is designed to track file processing positions, enabling restart resilience and exactly-once processing semantics.

## Core Components

The checkpointing system consists of four primary components that work together to maintain data and state consistency:

- **SqliteStateProvider**: Implements durable state persistence using SQLite
- **LiveStateService**: Maintains in-memory state as the source of truth
- **CheckpointDataSink**: Coordinates data writes with state updates
- **StateWriterService**: Monitors and logs checkpoint operations

These components follow a layered architecture where state updates flow from the data processing layer through in-memory caching to persistent storage.

## Atomic Update Guarantee

The checkpointing architecture provides atomic update guarantees by ensuring that state updates only occur after successful data persistence. This prevents scenarios where state advances without corresponding data being durably stored.

The atomicity is implemented through a coordinated sequence:

1. Data is written to Parquet files
2. Only upon successful write completion are checkpoint updates emitted
3. State updates are processed through the LiveStateService
4. SQLite persistence occurs asynchronously in batches

This sequence ensures that if a failure occurs during data writing, the state will not advance, allowing the system to resume from the last consistent checkpoint.

``mermaid
sequenceDiagram
participant Writer as CheckpointDataSink
participant Parquet as Parquet Storage
participant LiveState as LiveStateService
participant SQLite as SqliteStateProvider
Writer->>Parquet : Write data batch
Parquet-->>Writer : Success confirmation
alt Write successful
Writer->>LiveState : UpdatePosition(fileId, position)
Writer->>LiveState : Emit CheckpointPositionUpdate
LiveState->>SQLite : Queue batch update
SQLite->>SQLite : Execute in transaction
SQLite-->>LiveState : Batch persisted
else Write failed
Writer->>Writer : Throw exception
Writer->>System : Abort checkpoint update
end
```

## In-Memory State Management

The LiveStateService acts as the in-memory source of truth for file processing positions. It uses a thread-safe ConcurrentDictionary to store TrackedFileInfo objects, ensuring consistency across multiple worker threads.

Key features of in-memory state management:

- **Source of Truth**: The in-memory cache is authoritative, not the database
- **Thread Safety**: Uses AddOrUpdate pattern to prevent race conditions
- **Cache Hierarchy**: Falls back to persistent storage when cache misses occur
- **Update Filtering**: Only processes position updates when new positions are greater than current values

The service maintains a channel-based queue for checkpoint updates, allowing asynchronous processing while ensuring ordered delivery.

## SQLite Persistence Mechanism

The SqliteStateProvider implements durable state persistence using SQLite with several key features:

- **Atomic Transactions**: Uses explicit transactions for batch updates
- **Schema Management**: Ensures required tables exist on initialization
- **Conflict Resolution**: Uses UPSERT (INSERT ... ON CONFLICT DO UPDATE) semantics
- **Batch Processing**: Optimizes performance through batched writes

The provider implements the IStateProvider interface, allowing it to be easily substituted or decorated. It manages its own database connection and transaction lifecycle.

## Integration Patterns

The checkpointing components integrate through well-defined interfaces and patterns:

- **Dependency Injection**: Services are injected via constructor parameters
- **Channel-based Communication**: Uses System.Threading.Channels for async messaging
- **Interface Abstraction**: IStateProvider enables loose coupling
- **Record Types**: Immutable data transfer objects for checkpoint updates

The CheckpointDataSink coordinates between data processing and state management, ensuring that checkpoint updates are only emitted after successful data persistence.

## Practical Examples

### Example 1: Processing a Data Batch
```
csharp
// In CheckpointDataSink.WriteBatchAndCheckpointStateAsync
await WriteToParquetAsync(logEntries, partitionPath); // Data persistence first

// Only after successful write, emit checkpoint
await _liveStateService.UpdatePosition(
    dataBlock.FileId,
    dataBlock.VolumeSerial,
    dataBlock.EndPosition,
    dataBlock.FilePath,
    dataBlock.LastWriteTime
);

```

### Example 2: Reading Current Position
```
csharp
// In LiveStateService.GetPosition
if (_positionCache.TryGetValue((fileId, volumeSerial), out var trackedFile)) {
    return trackedFile.Position; // Fast in-memory lookup
}

// Fall back to persistent storage if not in cache
var persistentFile = await _persistentStateProvider.GetTrackedFileAsync(fileId, volumeSerial);

```

### Example 3: Batch State Update
```
csharp

    foreach (var update in updates) {

    }
    transaction.Commit(); // Atomic commit

## Troubleshooting Guidance

### Common Issues and Solutions

**Issue: Checkpoint updates not persisting to SQLite**
- **Cause**: LiveStateService persistence task has stopped
- **Solution**: Check application logs for exceptions in ProcessCheckpointUpdatesAsync
- **Verification**: Monitor the _checkpointChannel for backlog accumulation

**Issue: Data and state inconsistency after restart**
- **Cause**: Parquet write succeeded but checkpoint update failed
- **Solution**: The system will automatically recover by reprocessing from last checkpoint
- **Prevention**: Ensure adequate disk space and monitor WriteToParquetAsync exceptions

**Issue: Performance degradation with many files**
- **Cause**: In-memory cache grows without bounds
- **Solution**: Implement cache eviction policy or increase memory allocation
- **Monitoring**: Track _positionCache.Count and garbage collection frequency

**Issue: SQLite database locked errors**
- **Cause**: Multiple connections or long-running transactions
- **Solution**: Ensure transactions are kept short and connections are properly disposed
- **Configuration**: Consider using serialized threading mode for SQLite

### Monitoring and Health Checks

The system provides several built-in monitoring capabilities:

- **Metrics**: Static counters for log entries ingested, bytes processed, and checkpoints completed
- **Health Check**: SqliteStateProvider.CheckHealth() verifies database connectivity
- **Logging**: Detailed trace logs for checkpoint operations and persistence
