## Introduction
The `ILogParser` interface defines the contract for log parsing plugins within the LogTapestry system. It enables extensible parsing of various log formats by providing a standardized way to process raw log data into structured `LogEntry` objects. This interface is central to the ingestion pipeline, allowing developers to create custom parsers for different log formats while maintaining compatibility with the core system. The design leverages stream-based processing with internal buffering for efficient memory management.

## Interface Definition
The `ILogParser` interface is defined as an asynchronous disposable interface that represents an ongoing parsing session for a single file. It inherits from `IAsyncDisposable` to ensure proper resource cleanup when parsing is complete. The interface is located in the `LogTapestry.Core` namespace and serves as the foundation for all log format parsers in the system.


```csharp
public interface ILogParser : IAsyncDisposable
{
    Task<ParseChunkResult> ParseNextChunkAsync(Stream stream, CancellationToken token);
}
```


The interface includes two additional related interfaces:
- `IPositionAwareLogParser`: Extends `ILogParser` with position tracking capabilities for parsers that manage their own stream position
- `ILegacyLogParser`: Maintained for backward compatibility but marked for deprecation

## Method Signature and Parameters
The `ParseNextChunkAsync` method is the core of the `ILogParser` interface, responsible for reading from a `Stream` and parsing the next available set of log entries.

**Method Signature:**
```
csharp
Task<ParseChunkResult> ParseNextChunkAsync(Stream stream, CancellationToken token)

```

**Parameters:**
- **stream**: The input stream, positioned where the last read left off. The parser reads from the current position and is responsible for managing its internal buffering.
- **token**: A `CancellationToken` to allow cancellation of the parsing operation.

The method processes data in chunks, reading complete log entries from the stream and returning structured results. Unlike the previous `PipeReader`-based design, the current implementation uses internal buffering within the parser to handle partial entries and stream management.

## Role in Ingestion Pipeline
The `ILogParser` interface plays a critical role in the LogTapestry ingestion pipeline, acting as the bridge between raw log files and structured data processing. It is integrated into the system through the `FileReader` component, which orchestrates the parsing process.

``mermaid

FileReader->>DataBlockChannel : Yield final DataBlock if entries remain
FileReader->>LiveStateService : Update position for final DataBlock

```

**Diagram sources**
- [FileReader.cs](file://src/LogTapestry.Ingester/FileReader.cs#L100-L251)
- [FileEventProcessor.cs](file://src/LogTapestry.Ingester/FileEventProcessor.cs#L83-L107)

The ingestion flow is as follows:
1. `FileEventProcessor` receives file events and delegates to `FileReader`
2. `FileReader` determines the appropriate parser based on file path patterns
3. `FileReader` creates a parser instance using the factory pattern
4. `FileReader` opens the file stream and passes it to the parser
5. The parser processes chunks of data using internal buffering and returns `ParseChunkResult`
6. `FileReader` aggregates results into `DataBlock` objects and sends them to downstream components
7. Stream position is updated based on parser type (direct or position-aware)

### RegexLogParser
The `RegexLogParser` handles log formats that can be parsed using regular expressions. It supports both single-line and multi-line log entries through configuration.

**Key Features:**
- Uses `RegexOptions.Compiled` for performance-critical patterns
- Maintains state for multi-line log entries
- Processes up to 1,000 lines per chunk to prevent memory issues
- Handles various line ending formats (\n, \r, \r\n)
- Implements internal buffering using `BaseLogParser`'s buffer management

### CsvLogParser
The `CsvLogParser` handles CSV-formatted log files with configurable delimiters, quote characters, and field mappings.

**Key Features:**
- Supports quoted fields with escaped quotes
- Handles header rows and column mapping
- Configurable field type conversion (string, long, double, bool)
- Validates column counts and required fields
- Implements CSV-specific line parsing with quote handling

## Error Handling and Partial Results
The `ILogParser` interface is designed to handle parsing errors gracefully while preserving valid data. When a parsing error occurs, the implementation should:

1. Add the failed entry to the `Failures` collection in `ParseChunkResult`
2. Include detailed error information in the `ParsingFailure` object
3. Continue processing subsequent log entries
4. Return partial results containing both successful and failed entries


```csharp
// Example of error handling in CsvLogParser
catch (Exception ex)
{
    Logger?.LogWarning(ex, "Failed to parse CSV record: {Line}", line);
    return (null, CreateFailure($"CSV record parsing failed: {ex.Message}", line));
}
```


This approach ensures that isolated parsing errors do not prevent the processing of valid log entries, maintaining data integrity and availability.

## Performance Considerations
The `ILogParser` implementation must consider several performance aspects to handle large log files efficiently.

### Regex Compilation
The `RegexLogParser` uses `RegexOptions.Compiled` to improve performance for frequently used patterns:


```csharp
_startOfEntryRegex = _regexConfig.StartOfEntryRegex != null
    ? new Regex(_regexConfig.StartOfEntryRegex, RegexOptions.Compiled)
    : new Regex("^$", RegexOptions.Compiled);
```


This compiles the regex pattern to MSIL for faster execution, though it increases startup time and memory usage.

### Memory Usage
Both parser implementations use several techniques to minimize memory allocation:
- Reusable `StringBuilder` instances for line accumulation
- Internal byte buffer with efficient shifting and compaction
- Chunked processing to limit memory footprint
- Immutable collections for thread-safe result return

### Stream Processing
The use of direct `Stream` processing with internal buffering provides several performance benefits:
- Efficient memory management through buffer reuse
- Support for large files without loading entire content into memory
- Asynchronous processing to avoid blocking threads
- Position tracking integration with the ingestion pipeline

## Thread Safety and Lifecycle Management
The `ILogParser` instances are designed to be used in a single-threaded context per file. Each parser instance is created and used within the scope of processing a single file, ensuring thread safety through isolation rather than synchronization.

### Thread Safety
- Parser instances are not shared between threads
- Each file gets its own parser instance
- State is maintained per-file, preventing race conditions
- The ingestion pipeline uses consistent hashing to route file events to specific processors

### Lifecycle Management
Parser instances are managed through the Dependency Injection (DI) container and follow a scoped lifecycle:

## Implementation Guidance
When creating custom implementations of `ILogParser`, follow these guidelines:

1. **Inherit from BaseLogParser**: Use the base class for common functionality
2. **Use Stream efficiently**: Leverage internal buffering and avoid unnecessary allocations
3. **Handle errors gracefully**: Return partial results with failure details
4. **Manage memory carefully**: Use reusable buffers and avoid unnecessary allocations
5. **Implement proper disposal**: Clean up resources in `DisposeAsync`
6. **Consider performance**: Compile regex patterns and optimize critical paths
7. **Follow thread safety**: Assume single-threaded usage per instance
8. **Implement position awareness**: Consider implementing `IPositionAwareLogParser` for parsers with complex position tracking

Custom parsers should be registered in the parser factory dictionary in `FileReader` to be automatically discovered and used based on file patterns.
