## Introduction
LogTapestry is a log processing system designed for extensibility through a plugin architecture centered around the `ILogParser` interface. This document provides comprehensive guidance for developers who wish to extend the system by implementing custom log parsers for proprietary or complex log formats. The architecture supports both text-based and binary log formats, with built-in implementations for regex-based and CSV parsing. Developers can create new parsers by implementing the `ILogParser` interface and registering them in the configuration.

```
The LogTapestry plugin architecture is built around the `ILogParser` interface, which defines a contract for parsing log entries from a stream. The architecture follows a factory pattern where the `FileReader` service instantiates the appropriate parser based on the file's configuration. All parsers inherit from `BaseLogParser`, which provides common functionality such as buffer management, string conversion, and failure handling. The system supports multiple parser types through a registry of factory functions that map plugin types to concrete parser implementations.

A new interface, `IPositionAwareLogParser`, has been introduced for parsers that need to manage their own position tracking, which is useful when parsers wrap streams or use libraries that don't directly update stream position. The legacy `ILegacyLogParser` interface is maintained for backward compatibility but is marked for deprecation.
```

To implement a custom log parser, create a new class that inherits from `BaseLogParser` and implements the `ILogParser` interface. The primary method to implement is `ParseNextChunkAsync`, which reads from a stream and returns a `ParseChunkResult` containing successfully parsed entries and any failures. For JSON-formatted logs, the implementation would use a JSON parser to extract fields, while for binary formats, it would use binary deserialization. The parser should handle its own internal buffering to manage partial entries across multiple calls.

The `BaseLogParser` class has been enhanced with optimized buffer management, including efficient string decoding using `Decoder` and character buffers, which reduces memory allocations and improves performance. The base class now provides additional helper methods such as `IndexOfByte`, `BufferContainsAt`, and `AppendBufferToStringBuilder` to facilitate efficient parsing operations.

```
Custom parsers are registered through the `appsettings.json` configuration file. The `Plugins` array contains configuration objects for each parser type. To register a new parser, add a new entry to this array with a unique `Type` value that corresponds to the parser factory registration. The `IncludePatterns` and `ExcludePatterns` properties use glob patterns to determine which files the parser should handle. For JSON parsers, a configuration might look like:

```
json
{
  "Type": "json",
  "Name": "applicationJson",
  "IncludePatterns": [ "**/*.json", "**/*.log.json" ],
  "ExcludePatterns": [ ],
  "Config": {
    "TimestampProperty": "timestamp",
    "LevelProperty": "level",
    "MessageProperty": "message",
    "TimestampFormat": "yyyy-MM-ddTHH:mm:ssZ",
    "TimestampIsUtc": true,

```
The parser factory in `FileReader` uses the `Type` field to instantiate the appropriate parser. To add a custom parser type, modify the `ParserFactories` dictionary in `FileReader.cs` to include a factory function for the new type. The factory functions are defined as static delegates that create parser instances with proper dependency injection for logging.

## Best Practices for Parser Design

When designing custom log parsers, follow these best practices to ensure reliability, performance, and maintainability:

### Error Handling
Implement comprehensive error handling to gracefully manage malformed log entries. Never allow a single parsing failure to terminate the entire parsing process. Instead, capture the failure details in a `ParsingFailure` object and continue processing subsequent entries. Log warnings for parsing failures to aid in troubleshooting.

### Performance Optimization
Optimize parsers for high-throughput scenarios by minimizing memory allocations and using efficient parsing algorithms. Reuse buffers and collections where possible. For regex-based parsers, compile regular expressions with the `RegexOptions.Compiled` flag. Process data in chunks rather than loading entire files into memory. Utilize the optimized buffer management features in `BaseLogParser`, such as the pre-allocated `WorkingStringBuilder` and efficient string decoding with `Decoder`.

### Thread Safety
Ensure parsers are thread-safe when used in multi-threaded environments. Avoid shared mutable state between parser instances. If state must be shared, use appropriate synchronization mechanisms. The `ILogParser` interface is designed for single-file parsing sessions, so each parser instance should be dedicated to a single file.

### Buffer Management
Implement efficient buffer management to handle partial entries that span multiple read operations. The `BaseLogParser` provides a buffer and helper methods for this purpose. When reading from the stream, consume only the bytes that have been fully processed to avoid data loss. Use the `ReadIntoBufferAsync`, `IndexOfByte`, and `ConsumeBuffer` methods provided by the base class for optimal performance.

### Resource Disposal
Implement proper resource disposal by inheriting from `BaseLogParser` which implements `IAsyncDisposable`. Release any unmanaged resources in the `DisposeAsync` method. Use the `await using` pattern when creating parser instances to ensure proper disposal.
```

## Integration Points

### Custom State Providers
The system supports custom state providers through the `IStateProvider` interface. Implement this interface to store file processing state in alternative storage systems such as Redis, PostgreSQL, or cloud storage. The state provider is responsible for tracking file positions, last write times, and other metadata needed for incremental processing.

### Custom Data Sinks
Data sinks can be extended by modifying the `DataSink` class or creating new sink implementations. The current implementation writes data to Parquet files with a predefined schema. Custom sinks could forward data to message queues, databases, or monitoring systems. The `DataBlock` class contains the parsed log entries and can be processed by multiple sinks in parallel.

### Plugin Factory Registration
New parser types are integrated by adding factory functions to the `ParserFactories` dictionary in `FileReader`. This allows the system to instantiate the appropriate parser based on the configuration. The factory pattern enables loose coupling between the file processing logic and the specific parser implementations. Note that the legacy `ReadBlockOfLines` method has been marked as obsolete and should not be used in new implementations.

## Testing Extensions

The existing test framework in `LogTapestry.Core.Tests` provides a foundation for testing custom parsers. Use the `RegexLogParserTests` class as a template for creating tests for new parsers. Tests should verify both successful parsing of valid log entries and proper handling of malformed entries.


```csharp
[TestMethod]
public async Task JsonLogParser_ParsesValidJsonEntry()
{
    var pluginSettings = new PluginSettings {
        Type = "json",
        Name = "test_json",
        IncludePatterns = ["*.json"],
        JsonConfig = new JsonPluginConfig {
            TimestampProperty = "timestamp",
            LevelProperty = "level",
            MessageProperty = "message",
            TimestampFormat = "yyyy-MM-dd HH:mm:ss",
            FieldMappings = [
                new JsonFieldMapping { JsonProperty = "user_id", FieldName = "user_id", Type = "long" }
            ]
        }
    };

    await using var parser = new JsonLogParser(pluginSettings, "test.json");
    var jsonData = "{\"timestamp\":\"2025-08-18 16:00:01\",\"level\":\"INFO\",\"message\":\"User login\",\"user_id\":101}\n";
    var stream = new MemoryStream(Encoding.UTF8.GetBytes(jsonData));
    
    var result = await parser.ParseNextChunkAsync(stream, CancellationToken.None);
    
    Assert.AreEqual(1, result.SuccessfulEntries.Count);
    Assert.AreEqual(0, result.Failures.Count);
    
    var entry = result.SuccessfulEntries[0];
    Assert.AreEqual("INFO", entry.Level);
    Assert.AreEqual(101L, entry.Fields["user_id"]);
    Assert.AreEqual("test.json", entry.Source);
}
```


Integration tests in `LogTapestry.Integration.Tests` validate the end-to-end data lifecycle, including ingestion, compaction, and querying. These tests can be extended to verify that custom parsers work correctly within the full processing pipeline.
