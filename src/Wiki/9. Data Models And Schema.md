## LogEntry Data Model

The `LogEntry` class represents the fundamental unit of log data within the LogTapestry system. It is a C# record that encapsulates a single, structured log event after successful parsing. This canonical object is the primary data structure that flows through the ingestion pipeline to the data sink.

The `LogEntry` record is defined with the following fields:

- **Timestamp**: A `DateTime` value representing the exact time when the log event occurred.
- **Level**: A `string` indicating the severity level of the log (e.g., "INFO", "ERROR", "DEBUG").
- **Message**: A `string` containing the main textual content of the log message.
- **Source**: A `string` that identifies the file or component from which the log originated.
- **TemplateHash**: A `long` integer used to identify the message pattern or template, which can be useful for log deduplication and analysis.
- **Fields**: An `IReadOnlyDictionary<string, object>` that holds dynamic, structured properties extracted from the log message. This allows for flexible schema support, accommodating various log formats with different metadata.
- **Ulid**: A `byte[]` array that stores a Universally Unique Lexicographically Sortable Identifier. This field has a default parameter value of `null`, but the record includes a property that initializes it with a new ULID if none is provided, ensuring every log entry has a unique identifier.


```csharp
public record LogEntry(DateTime Timestamp,
    string Level, string Message, string Source,
    long TemplateHash,
    IReadOnlyDictionary<string, object> Fields,
    byte[]? Ulid = null)
{
  public byte[] Ulid { get; init; } = Ulid ?? System.Ulid.NewUlid().ToByteArray();
}
```


This design promotes immutability and thread safety, which are critical for a high-throughput logging system. The use of a record ensures that the data structure is concise and that value-based equality is automatically provided.

## DataBlock Container

The `DataBlock` class serves as a batch container for multiple `LogEntry` objects, designed to improve I/O efficiency and provide essential file context metadata for checkpointing. It is a key component in the data flow between the file reader and the data sink.

A `DataBlock` contains the following properties:

- **FileId**: A `ulong` that uniquely identifies the source log file on the filesystem.
- **VolumeSerial**: A `long` representing the volume serial number of the drive where the file resides, used in conjunction with `FileId` for a globally unique file identifier.
- **FilePath**: A `string` containing the full path to the source log file.
- **EndPosition**: A `long` indicating the byte offset in the file after the last log entry in this block was read. This is crucial for resuming ingestion from the correct position after a restart.
- **LastWriteTime**: A `DateTime` value capturing the last modification time of the file when this block was read, used to detect file rotation or truncation.
- **Entries**: An `IReadOnlyList<LogEntry>` that holds the collection of log entries parsed from a segment of the source file.

The `DataBlock` structure ensures transactional consistency by bundling log data with its positional context. This allows the system to atomically update the processing state only after the corresponding data has been successfully persisted.


```csharp
public record DataBlock(
    ulong FileId,
    long VolumeSerial,
    string FilePath,
    long EndPosition,
    DateTime LastWriteTime,
    IReadOnlyList<LogEntry> Entries
);
```


Additionally, the codebase includes a `CheckpointPositionUpdate` record, which extends the positional data with a `CheckpointTime` to track when a state update was durably committed, further enhancing the reliability of the checkpointing mechanism.

## SQLite State Database Schema

The `SqliteStateProvider` class implements the `IStateProvider` interface to manage persistent state using an SQLite database. This state database is critical for tracking the progress of log file ingestion and maintaining metadata about the stored data.

The schema consists of three primary tables:

### TrackedFiles Table
This table stores the processing state for each ingested log file, using a composite primary key of `VolumeSerial` and `FileId` for efficient lookups.

| Column Name | Data Type | Description |
| :--- | :--- | :--- |
| VolumeSerial | INTEGER | The serial number of the file's volume. |
| FileId | INTEGER | The unique identifier of the file. |
| FilePath | TEXT | The full path to the log file. |
| Position | INTEGER | The current byte offset position in the file. |
| LastWriteTimeUtc | INTEGER | The file's last write time, stored as a Unix timestamp. |

### FieldSchema Table
This table acts as a schema registry for dynamically extracted log fields, enabling schema evolution and type consistency.

| Column Name | Data Type | Description |
| :--- | :--- | :--- |
| FieldName | TEXT | The name of the extracted field (primary key). |
| FieldType | TEXT | The data type of the field ("string", "long", "double", "bool"). |

### ParquetFiles Table
This table indexes all written Parquet files, providing metadata for data discovery and management.

| Column Name | Data Type | Description |
| :--- | :--- | :--- |
| Id | INTEGER | Auto-incrementing primary key. |
| FilePath | TEXT | The full path to the Parquet file. |
| Partition | TEXT | The time-based partition path (e.g., "year=2023/month=12/day=01"). |
| RowCount | INTEGER | The number of log entries in the file. |
| SizeBytes | INTEGER | The file size in bytes. |
| CreatedUtc | INTEGER | The creation time as a Unix timestamp. |

The `SqliteStateProvider` uses upsert operations (`INSERT ... ON CONFLICT DO UPDATE`) to ensure atomic state updates, which is essential for maintaining data integrity in a concurrent environment.

## Parquet File Organization

Log data is stored in the Parquet columnar storage format, which is optimized for efficient querying and compression. The system uses time-based partitioning to organize Parquet files, enhancing query performance by allowing partition pruning.

### Parquet Schema
The Parquet schema is defined in the `ParquetSink` class and includes both top-level fields and a nested structure for dynamic properties.

- **Top-Level Fields**:
  - `Timestamp` (DateTime)
  - `Level` (String)
  - `Message` (String)
  - `Source` (String)
  - `TemplateHash` (Long)
  - `Ulid` (Byte Array)

- **Nested Fields**:
  - `Fields` (List of Struct): A list containing dynamic fields with the following structure:
    - `Key` (String): The field name.
    - `StringValue` (String, optional): Value if the field is a string.
    - `LongValue` (Long, optional): Value if the field is a long integer.
    - `DoubleValue` (Double, optional): Value if the field is a double.
    - `BoolValue` (Bool, optional): Value if the field is a boolean.

This schema uses a union-like pattern with nullable fields to store values of different types within a single columnar structure, which is a common practice in Parquet for handling semi-structured data.

### Time-Based Partitioning
Parquet files are organized into a directory hierarchy based on the timestamp of the log entries they contain, typically following a pattern like `year=YYYY/month=MM/day=DD/landing/`. This partitioning strategy allows the query engine to scan only the relevant directories for time-range queries, significantly reducing I/O.

### Schema Evolution
The system supports schema evolution through the `FieldSchema` table in the SQLite database. When a new field is encountered during ingestion, its name and inferred data type are recorded. The data type is determined by the first non-null value of the field, using the following rules:
- `long` for integer values
- `double` for floating-point values
- `bool` for boolean values
- `string` for all other types

Once a field's type is established, it remains consistent, ensuring query stability.

## Field Schema Management

Field schema management is a critical feature that enables the system to handle logs with dynamic and evolving structures. The `FieldSchema` table in the SQLite database serves as a centralized schema registry.

### Schema Population
The `PopulateFieldSchemaAsync` method in the `ParquetSink` class is responsible for updating the schema registry. For each batch of `LogEntry` objects:
1. It extracts all unique field names from the `Fields` dictionary.
2. For each new field (not already in the `FieldSchema` table), it infers the data type from the first non-null value.
3. It inserts the `FieldName` and `FieldType` into the `FieldSchema` table.

This process ensures that the schema is automatically discovered and recorded without requiring manual configuration.

### Schema Utilization
The `GetFieldTypeAsync` method allows other components, such as the query engine, to retrieve the data type of a field. This information is essential for:
- Correctly parsing and interpreting data from Parquet files.
- Validating queries and preventing type mismatches.
- Providing accurate metadata in query results.

The schema management system is designed to be append-only; once a field's type is set, it is not changed, which maintains data consistency. However, this also means that if a field's type changes in the source logs, the system will use the type of the first occurrence, which could lead to data loss for subsequent values of a different type.

## Data Access Patterns and Performance

The chosen storage models are designed to optimize for high-throughput ingestion and efficient querying.

### Ingestion Performance
- **Batching**: Log entries are processed in `DataBlock` batches, reducing the number of I/O operations and database transactions.
- **Asynchronous I/O**: The `WriteBatchAsync` method uses asynchronous operations to write to Parquet files and update the state database, preventing blocking and maximizing throughput.
- **Efficient Data Shredding**: The `NestedListShredder` class efficiently converts the nested `Fields` dictionary into Parquet's columnar format using specialized `ColumnBuilder` classes for each data type, minimizing memory allocations and processing time.

### Query Performance
- **Columnar Storage**: Parquet's columnar format allows queries to read only the columns they need, significantly reducing disk I/O.
- **Partition Pruning**: Time-based partitioning enables the query engine to skip entire directories of data that fall outside the requested time range.
- **Indexing**: The `ParquetFiles` table in SQLite provides a catalog of all data files, allowing the query engine to quickly locate relevant files without scanning the entire filesystem.

## Data Lifecycle and Retention

The data lifecycle in LogTapestry is managed through a three-stage workflow:

1. **Ingestion**: The `Ingester` service reads log files, parses entries, and writes them to Parquet files in the data directory while updating the SQLite state database.

2. **Compaction**: The `Compactor` tool optimizes the Parquet files by merging smaller files into larger ones, improving query performance and reducing filesystem overhead. It can be configured to compact files older than a specified timespan (e.g., `--compact-older-than 1h`).

3. **Querying**: The `Query` tool allows users to execute SQL queries against the ingested data, using the SQLite database to locate relevant Parquet files and the Parquet reader to extract the data.

The README.md outlines this end-to-end workflow, emphasizing that the full data lifecycle can be validated through integration tests. While specific retention policies (e.g., automatic deletion of data older than 30 days) are not explicitly defined in the provided code, the `Compactor`'s `--compact-older-than` parameter suggests that time-based data management is a core concept. A retention policy could be implemented as an extension of the compactor, which would delete Parquet files and their corresponding entries in the `ParquetFiles` and `TrackedFiles` tables after a certain period.
