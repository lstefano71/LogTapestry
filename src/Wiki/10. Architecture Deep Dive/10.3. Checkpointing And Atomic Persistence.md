## Introduction
The LogTapestry system implements a robust checkpointing mechanism to ensure data consistency between Parquet data files and SQLite state records. This document details the atomic persistence strategy, focusing on the coordination between the `CheckpointDataSink`, `SqliteStateProvider`, and `LiveStateService` components. The system guarantees that data writes and state updates are committed atomically using a two-phase commit pattern with temporary file staging and state versioning.

## Core Components Overview
The checkpointing system is composed of several key components that work together to ensure data integrity:

- **CheckpointDataSink**: Coordinates atomic updates between Parquet data files and SQLite state records.
- **SqliteStateProvider**: Manages persistent state storage in SQLite, tracking file processing offsets.
- **LiveStateService**: Maintains an in-memory cache of file positions as the source of truth, with asynchronous persistence to SQLite.
- **StateWriterService**: Monitors and logs checkpoint updates for observability.

These components implement a transactional model where data persistence precedes state updates, ensuring that no data is lost due to partial commits.

## Two-Phase Commit Pattern
The checkpointing mechanism implements a two-phase commit pattern to ensure atomicity between data and state persistence. This pattern consists of:

1. **Phase 1: Data Persistence (Prepare Phase)**
   - Data is written to Parquet files using temporary staging
   - Files are written with a `.parquet_tmp` extension
   - Only after successful write completion is the file atomically moved to its final `.parquet` location

2. **Phase 2: State Commit (Commit Phase)**
   - After successful data persistence, checkpoint updates are emitted
   - State updates are first applied to in-memory cache in `LiveStateService`
   - Updates are then queued for asynchronous persistence to SQLite

The implementation in `CheckpointDataSink.WriteToParquetAsync` demonstrates this pattern:


```csharp
private async Task WriteToParquetAsync(LogEntry[] batch, string partitionPath)
{
    Directory.CreateDirectory(partitionPath);
    var tempFilePath = Path.Combine(partitionPath, $"part-{Guid.NewGuid()}.parquet_tmp");
    var finalFilePath = Path.ChangeExtension(tempFilePath, ".parquet");

    long bytesWritten = 0;
    try {
        using (var stream = File.Create(tempFilePath)) {
            await WriteBatchAsync(batch, stream, finalFilePath, partitionPath);
            bytesWritten = stream.Length;
        }

        // Stream is now closed, safe to move the file
        File.Move(tempFilePath, finalFilePath);
        Metrics.BytesProcessed += bytesWritten;
    } catch {
        // Clean up temp file on error
        if (File.Exists(tempFilePath)) {
            File.Delete(tempFilePath);
        }
        throw;
    }
}
```


The atomic file move operation ensures that only completely written files become visible, preventing partial file reads.

## Failure Recovery Scenarios
The checkpointing system handles various failure scenarios to maintain data consistency:

### Crash During Write
If a crash occurs during Parquet file writing:
- The temporary file (`.parquet_tmp`) remains on disk
- On restart, the system ignores temporary files
- The corresponding state update was never emitted (due to phase ordering)
- Data ingestion resumes from the last checkpointed position

### Partial Commits
The system prevents partial commits through strict phase ordering:
- State updates are only emitted after successful data persistence
- If data write fails, the exception propagates and state update is skipped
- The `WriteBatchAndCheckpointStateAsync` method wraps the entire operation in a try-catch block, ensuring atomic failure

### Idempotent Replay
Checkpoint updates are designed to be idempotent:
- The `LiveStateService.UpdatePosition` method uses `AddOrUpdate` with position comparison
- Only updates with higher positions are applied
- This prevents duplicate processing when replaying from failure


```csharp
_positionCache.AddOrUpdate(key,
    // Add new entry
    _ => {
        updated = true;
        return new TrackedFileInfo { /* ... */ };
    },
    // Update existing entry only if new position is greater
    (existingKey, existingFile) => {
        if (position > existingFile.Position) {
            updated = true;
            return new TrackedFileInfo { /* ... */ };
        }
        return existingFile;
    });
```

## State Management with SqliteStateProvider
The `SqliteStateProvider` class implements the `IStateProvider` interface to manage persistent state in SQLite. It tracks file processing information through the `TrackedFileInfo` structure:


```csharp
public class TrackedFileInfo
{
    public long VolumeSerial { get; set; }
    public ulong FileId { get; set; }
    public string FilePath { get; set; }
    public long Position { get; set; }
    public System.DateTime LastWriteTimeUtc { get; set; }
}
```


Key responsibilities include:
- **State Persistence**: Storing file processing offsets in the `TrackedFiles` table
- **Schema Management**: Maintaining field type information in `FieldSchema` table
- **File Metadata**: Tracking Parquet file creation in `ParquetFiles` table

The provider uses SQLite's `ON CONFLICT DO UPDATE` syntax for upsert operations, ensuring thread-safe state updates:


```csharp
cmd.CommandText = @"
    INSERT INTO TrackedFiles (VolumeSerial, FileId, FilePath, Position, LastWriteTimeUtc)
    VALUES (@volumeSerial, @fileId, @filePath, @position, @lastWriteTimeUtc)
    ON CONFLICT(VolumeSerial, FileId) DO UPDATE SET
        FilePath=excluded.FilePath,
        Position=excluded.Position,
        LastWriteTimeUtc=excluded.LastWriteTimeUtc;
";
```


The `LiveStateService` enhances this with an in-memory cache, making it the source of truth for current positions while delegating durability to SQLite.

## Performance Implications and Tuning
The checkpointing system has several performance characteristics and tuning options:

### Synchronous vs. Asynchronous Checkpointing
- **Synchronous**: Data write and state update occur in the same thread
  - Pros: Stronger consistency guarantees
  - Cons: Higher latency, blocks data ingestion
- **Asynchronous**: State updates are queued for background processing
  - Pros: Better throughput, non-blocking
  - Cons: Slight delay in state persistence

LogTapestry uses an asynchronous model via the `_checkpointChannel` in `LiveStateService`, allowing high-throughput data ingestion while ensuring eventual consistency.

### Checkpoint Frequency Strategies
The system can be tuned through several parameters:
- **Batch Size**: Larger batches reduce checkpoint frequency but increase recovery time
- **Checkpoint Interval**: Time-based or volume-based triggering
- **Batch Processing**: The `ProcessCheckpointUpdatesAsync` method processes updates in batches of 100


```csharp
// Process in smaller batches to avoid holding locks too long
if (batch.Count >= 100) {
    await PersistBatch(batch);
    batch.Clear();
}
```


### Performance Metrics
The system tracks key metrics for monitoring:
- `LogEntriesIngested`: Total log entries processed
- `BytesProcessed`: Total bytes written to Parquet
- `CheckpointsCompleted`: Number of successful checkpoints

These metrics help identify bottlenecks and optimize checkpoint frequency.

## Data Deduplication and Corrupted State Recovery
The system includes mechanisms for data deduplication and state recovery:

### Data Deduplication Logic
The `LiveStateService` prevents duplicate processing by comparing positions:
- Only updates with positions greater than the current value are applied
- This handles scenarios where the same data block is processed multiple times
- Position comparison ensures monotonic progression

### Corrupted State Recovery
The system can recover from corrupted state through:
- **In-Memory Cache as Source of Truth**: The primary state is in memory, reducing reliance on disk
- **State Reconciliation**: On startup, the service loads state from SQLite but prioritizes in-memory data
- **Checkpoint Validation**: The `CheckpointPositionUpdate` includes timestamp metadata for durability tracking

When restarting after a crash:
1. The in-memory cache is empty
2. State is loaded from SQLite via `GetAllTrackedFilesAsync`
3. Data ingestion resumes from the last persisted position
4. Any data written but not checkpointed is reprocessed (idempotent)

The system assumes that data ingestion is idempotent, which is reasonable for log processing where duplicate entries can be filtered during querying.
